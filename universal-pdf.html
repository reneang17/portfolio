Universal PDF Reader

Experience-Driven PDF.js Viewer (3 Iterations)

View on GitHub Live Demo

Problem statement: why most PDF readers still feel “worse than paper”

Most PDF viewers optimize for document display, not reading experience:

  • Navigation is often generic (scroll + search) instead of study-friendly (semantic sections, quick jumps).
  • Large documents can feel sluggish without virtualization and careful rendering pipelines.
  • Many custom viewers lose essential affordances (text selection, links, annotations).
  • “Dark mode” is common, but few tools explore lighting, attention, and comfort—the things that make physical reading enjoyable.

My goal is a universal PDF reader (web-native, cross-device, powered by PDF.js) that competes on both technical portability and reading experience.

Architectural evolution across iterations

Iteration 1 — ForestViewer: prove UX beyond “open and scroll”

ForestViewer is a book-specific study reader that treats navigation as the core feature: random access, chapter/section jumps, and verse-driven entry points. It demonstrates that a PDF reader can be designed like a learning tool, not just a file viewer.

Key idea proved: structured navigation and random access can be a primary UX primitive, especially for reference books and study workflows.

Iteration 2 — POC: move from a single book to a library system

API Repo UI Repo Demo

The second iteration focuses on componentization and scale-out architecture:

  • A reusable React PDFViewer composed of small units (upload, selector, navigation, canvas renderer).
  • A library workflow: fetch list of PDFs from an API and load a selected PDF via a download URL endpoint.
  • Correct HiDPI rendering behavior using device pixel ratio scaling.

Key idea proved: a universal reader needs a system boundary—viewer runtime separated from storage/auth via a stable API contract.

Iteration 3 — Spotlight Reader: build a real viewer engine + immersive reading modes

The third iteration becomes a foundation for a product:

  • Built @bridge-pdf/core, exporting a framework-agnostic viewer engine (BridgePDF) plus a theme controller (ThemeController).
  • Implemented virtualized rendering:
    • Create page placeholders
    • Render pages lazily using IntersectionObserver
    • Track current page with a second observer
  • Added multi-layer support:
    • Canvas rendering
    • Text layer (pdfjsLib.TextLayer)
    • Annotation/link layer with viewport coordinate mapping
  • Added a dedicated thumbnail pipeline with lazy rendering and page sync.
  • Introduced Paper/Dark/Lamp/Spotlight modes:
    • Theme toggles in ThemeController
    • Spotlight position tracked using ResizeObserver + animation frames and stored in CSS vars (--spotlight-x)
    • Lamp/Spotlight overlays implemented via CSS radial gradients and a paper tint overlay using blend modes
Repo Demo

Key idea proved: “reading experience” can be engineered: a rendering engine plus a perceptual layer (lighting/comfort modes).

Technical decisions (what I optimized for)

  • Cross-platform: JavaScript + PDF.js (browser-first portability). PDF.js’s model (document → page → viewport → canvas render) is the core primitive.
  • Performance for large PDFs: virtualization via IntersectionObserver rather than eager rendering all pages.
  • Preserve PDF affordances: text and annotation layers rather than “canvas-only” rendering.
  • Reusable architecture: package core viewer logic separately from the demo app.
  • Experience experimentation: Lamp/Spotlight modes implemented as a controllable theme system, not a one-off UI trick.

UX experimentation & research

This project is deliberately iterative: each version answers a question.

  • Can a PDF reader feel like a study tool? (ForestViewer)
  • What does a library-ready PDF platform boundary look like? (POC: API + component viewer)
  • What would it take to compete with native reading comfort? (Spotlight: virtualization + perceptual modes)

AI-assisted engineering methodology

Honest + strategically framed

I’m not a senior engineer, so I developed this using AI-assisted workflows (LLMs as a debugging partner, refactoring assistant, and research accelerator). The value isn’t “AI wrote the code”—it’s that I used modern tools to iterate faster while I owned:

  • system decomposition (core vs app),
  • performance strategy (virtualization),
  • correctness boundaries (worker setup, layers),
  • product decisions (navigation primitives, reading comfort modes),
  • and shipping working demos.
